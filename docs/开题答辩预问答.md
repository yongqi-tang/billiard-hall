# 开题答辩预问答（一页速查）

> 项目：基于微信小程序的台球厅预约管理系统
> 技术栈：Spring Boot 2.7 + MyBatis-Plus + MySQL 8 + 原生微信小程序 + Vue3（管理后台，本地引入）
> 核心链路：扫码开台 → 自动亮灯 → 自助计时 → 自动结账 → 自动灭灯，外加在线预约

---

## 一、选题与创新点

**Q1：市面上同类系统很多，你的特色是什么？**
A：不是普通的信息管理系统，而是"无人自助"闭环：扫码即开台、系统自动计费、余额制自助结账、定时任务自动处理欠费；在此基础上新增**在线预约**，并与扫码开台自动衔接（预约自动核销），强调无人值守 + 翻台率。

**Q2：为什么选这个题目？**
A：无人台球厅是线下文娱降本趋势；微信小程序免安装、扫码即用；校园/社区场景需求真实。技术上也覆盖了小程序 + 后端 + 数据库全栈，适合毕设体量。

**Q3：课题实用价值？**
A：降人力成本、免收银、预约减少顾客空等、翻台率提升。同类模型可复用到棋牌室、KTV、网吧等计时场所。

---

## 二、技术选型

**Q4：为什么用 Spring Boot + MyBatis-Plus？**
A：约定优于配置、启动快；MyBatis-Plus 内置 CRUD 与逻辑删除，减少样板代码；生态成熟、资料多。单体架构对毕设规模足够，不用微服务自增复杂度。

**Q5：管理后台为什么是单 HTML，不用前后端分离？**
A：为简化部署——单 HTML + 本地 Vue3 可嵌入后端静态资源，浏览器直接访问 `/admin/index.html`，避免跨域与单独部署。小程序端（用户端）才是系统核心，管理后台做运营辅助。

**Q6：微信登录怎么实现的？**
A：小程序 `wx.login` 拿 code → 后端调微信 `code2session` 换 openid → 按 openid 查/建用户。开发模式（code 以 `dev_` 开头或未配置真实 appid）直接生成 `dev_openid_xxx` 跳过真实调用，方便本地联调。

**Q7：数据库几张表？怎么设计？**
A：6 张核心表：用户表、球台表、预约表、订单表、充值流水表、设备表。订单与球台、用户外键关联；**预约表独立成表**（记录用户/球台/日期/起止时间/状态），因为预约是"时间段资源"管理，和订单生命周期不同。

## 三、核心业务（重点）

**Q8：计费规则怎么算的？**
A：`起步价(含N分钟) + 超时按分钟单价`，规则在 `application.yml` 可配置（起步价 30 元含 30 分钟，超出每分钟 1 元；球台可设自己的起步价/时价）。开台先扣起步价，结账按真实时长算总额，**多退少补**。

**Q9：多人同时预约同一球台同一时段怎么办？**
A：三层防护：① 业务层"先查后插"——查同球台同日期、时间区间重叠（`start < 新end 且 end > 新start`）且状态为待使用/已开台的记录，有则拒绝；② 同一用户同时段去重（防刷单）；③ 整个创建包在 `@Transactional` 事务里，数据库唯一约束兜底。

**Q10：预约了不来怎么办？**
A：定时任务（每 60 秒）扫描：开台宽限 **30 分钟**未到店 → 自动释放（状态置"超时释放"）；预约时段已过仍未开台 → 置"已完成"。释放后球台自动回到可预约，不浪费资源。

**Q11：预约和扫码开台怎么衔接？**
A：扫码开台时自动执行"预约核销"——查当前用户在该球台当前时段是否有待使用预约，有则核销并允许开台；若球台处于预约态但用户没有本时段有效预约（被他人预约了），则拒绝开台。球台状态：空闲(0)→使用中(1)→空闲，预约态(3)只对持有效预约者开放。

**Q12：预约状态有哪几种？**
A：5 种：0 待使用 / 1 已开台 / 2 已完成 / 3 已取消 / 4 超时释放。前段可提前 10 分钟到店核销开台，超 30 分钟宽限自动释放。

**Q13：硬件（灯控）怎么做的？**
A：抽象了 `DeviceService` 接口（`turnOnOff/isOn`），现在用 `MockDeviceService` 跑通全流程；后续替换涂鸦/机智云/ESP8266 实现即可，**业务代码零改动**。

## 四、并发与可靠性

**Q14：并发下单/开台会不会出错？**
A：关键写操作都包 `@Transactional`；预约冲突走"先查后插 + 唯一约束兜底"；开台校验"同一用户同时只能一台球局"。在测试中专门用预约冲突用例验证过。

**Q15：服务器宕机/重启，进行中的球局怎么办？**
A：计时不依赖前端倒计时，结账按订单 `start_time` 到当前时间实时计算真实时长，重启不影响已用时长；欠费标记存内存 Map，重启后由定时任务重新扫描补齐。

**Q16：数据一致性怎么保证？**
A：数据库事务 + 逻辑删除；金额变动全部走充值流水表（`recharge_record`）留痕，对账可追溯。

**Q17：哪些是现成的，你自己的工作量在哪？**
A：框架（Spring Boot/MyBatis-Plus/Vue3）是现成的，但核心是自己设计实现的：计费模型与多退少补、预约时间段冲突算法与 5 状态流转、扫码开台与预约自动核销衔接、欠费强制结算定时任务、设备/支付接口抽象、三端接口设计与联调，以及配套测试。

**Q18：进度安排合理吗？**

## 六、测试与后续

**Q19：系统怎么测试的？**
A：4 类测试（Node 可跑）：计费算法边界测试、模拟后端端到端测试、预约逻辑测试（冲突/取消/核销）、真实后端接口集成测试（需先启动后端）。预约流程另做了端到端手测：创建→冲突拦截→核销→结账→球台状态复原。

**Q20：哪些还没做、后续计划？**
A：① 真实微信支付（需企业主体商户号，当前为余额模拟制）；② 真实硬件联动（ESP8266/涂鸦灯控，当前 mock）；③ 小程序真机部署与 HTTPS 域名接入；④ 高并发下引入 Redis 存计时状态（当前内存兜底）。
